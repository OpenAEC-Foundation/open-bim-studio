This sheet shows the working hypothesis: instead of building on an existing kernel, a new geometry kernel is written in DynLex, followed by a UI library and an IFC library in the same language. The kernel aims at the representational breadth of a B-rep kernel, the speed of a mesh modeller, and the numeric accuracy of engineering CAD — with every coordinate in 64-bit and every combinatorial decision exact. Every fundamental choice on this sheet is to be substantiated by a traceable research note — a side-by-side study of the open-source kernels, their problems and the causes of those problems — before its decision record is accepted.

§ 0

Evidence before decisions

Nothing on this sheet is decided. Each fundamental choice maps to a research question; the question is answered by a candidate note or a measured spike; the answer fills a cell of the decision record's evidence table. A record with an empty cell stays proposed, and the kernel milestones stay blocked.

§ 1

One monorepo, three libraries, then the application

The kernel comes first because both other libraries depend on it and because it carries the largest unknowns: robustness of booleans, precision, performance. The UI and IFC libraries get their own design specs once the kernel has something for them to consume.

§ 2

Four equal representations, explicit conversions

No representation is the source of the others. The caller chooses per object; the kernel never converts silently. Each conversion is a named operation with its own parameters and failure modes.

§ 3

Coordinates never get large, decisions never get wrong

All kernel coordinates are 64-bit floating point in a tile-local frame. Unbounded extent comes from many small frames, not one distant origin — the pattern IfcMapConversion already standardises. Only the GPU module produces 32-bit values, camera-relative, at upload time.

§ 4

Thirteen modules, one direction

Each module has one purpose, a public .dl surface, private files marked local, and its own tests/. A module may import only from the layers below it.

§ 5

Where the speed comes from

Data-oriented layout

Every representation is structure-of-arrays. Entities are addressed by generational handles (index + generation): O(1) delete, stable across reallocation, dangling references detected rather than dereferenced.

Index everything

BVH over B-rep faces and mesh triangles, octree over point-cloud chunks, tile grid over objects. Every ray, box or nearest query goes through an index.

Parallel for

Tessellation of many solids, normals, booleans of many pairs, octree build. Needs DynLex runtime threading (M7); until then the same code runs serially and correctly.

GPU compute in DynLex

DynLex compiles to SPIR-V. Instanced tessellation, normal generation, culling and point-cloud LOD selection are compute kernels in gpu/, dispatched by ui/.

§ 6

What DynLex must grow

DynLex is the maintainer's own language: natural-language-like patterns, static typing with full inference, RAII memory, data-only classes, LLVM native and SPIR-V back ends, a Vulkan runtime. The kernel will be the largest program it has carried. Compiler defects are minimised, root-caused and fixed in the dynlex repository — never worked around in the kernel.

§ 8

M0 — the plan on the table

Seven tasks, each ending in a verifiable state and one commit. Task 0 is a prerequisite with no commit and is the expensive one: no compiler is built in the sibling checkout and the CI publishes no per-commit artefacts, so the pinned LLVM fork has to be built once — unless an already-built compiler elsewhere is pointed to through DYNLEX_ROOT.
