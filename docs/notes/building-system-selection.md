# Selecting a flat system's contour points and edges

**Decision question:** which point/edge interactions are already usable on a
flat ceiling while corrected whole-object corner/side grips remain pending?

The existing native boundary sketch supports the workflow below. This is a
verified current interaction, not delivery of the eight requested shape grips
on ordinary object selection. That correction remains
[issue #30](https://github.com/OpenAEC-Foundation/open-bim-studio/issues/30).

## Current workflow

1. Open the **3D** view and select the whole building system. If a panel is
   selected, Escape returns to its carrier before entering the sketch.
2. Press **Tab** to edit its contour. The magenta contour corners follow the
   displayed ceiling plane.
3. Click a **corner**. Properties shows **Point X** and **Point Y**, in the
   contour's local coordinates. Click the body/middle of an **edge** to select
   that edge independently of its vertices.
4. Press **G**, move the mouse, then click to place the pending change.
   During the move, **Escape** cancels that move and retains the sketch selection.
5. Press **Tab** to apply the contour. One **Undo** restores the previous
   contour; one **Redo** reapplies the operation.

In the idle sketch Pick state, Escape leaves the sketch without applying its
pending changes. Escape is therefore not a prerequisite before selecting the
first point or edge. This distinction matters when following older examples.

The ordinary generic control-point grips still have a known positioning problem
on flat systems. They are separate from the contour's corner markers. No new
side-midpoint grip shape, hover mode or ordinary-selection eight-grip layout
has been implemented by this verification.

## Measured native behaviour

The existing Linux application binary from `2b58b0f` was exercised with real
3D mouse/keyboard events and API observations/Undo/Redo, on an independent copy
of the two-LED sample generated by [PR #34](https://github.com/OpenAEC-Foundation/open-bim-studio/pull/34).
The host is a 4800 x 3600 mm ceiling at 2600 mm relative elevation, with 600 mm
modules. No active user document was operated and no editor code was changed.

**20 GUI/API assertions passed**, including:

- Selecting the original corner at local (0, 0); G preview leaves its committed
  coordinates and undo depth unchanged; Escape retains the original point.
- Placing that corner at (300, 300) mm in the pending sketch; Tab applies four
  valid joined segments as one operation. Reopening the sketch reads the moved
  coordinates; Undo/Redo restore (0, 0)/(300, 300) respectively.
- Selecting an edge at its midpoint without selecting a vertex. G preview and
  Escape behave independently of point selection.
- Moving the edge translates both ends to the same local X, with the opposite
  endpoints unchanged. The screen-coordinate test produced X = 299 mm at both
  ends; it did not assume a fixed pixel displacement means exactly 300 mm.
  Undo restores X = 0 and Redo restores the measured displacement at both ends.
- Returning the test document to its original contour and host ID, then leaving
  a corner selected in the separate visible demonstration window.

The API's `click X Y` is a plan-pointer operation. In this boundary mode it can
answer “Draw the contour in the 3D view, on the system's face”; that response is
not proof that native 3D point selection is broken. The successful audit used
native 3D mouse picking and ordinary keys rather than treating that plan command
as a world-space sketch hit. Coordinates, messages, undo depth and retained
InputV1 were checked; this audit does not claim a complete serialized-model diff
or a new compiled DynLex regression fixture.

## Numeric input and refusal check

A separate disposable native process on the same `2b58b0f` binary passed
**9 additional checks**. A corner was picked in 3D; the supported property API
set Point X and Point Y to exactly 300 mm. Tab committed the change as one
operation. Reopening the contour read the committed (300, 300) mm point.

Changing its pending X to -100 mm and pressing Tab produced
“Sketch not finished: keep the contour between the system's ends and above its
foot”. Undo depth stayed at one. Leaving that refused sketch and reopening it
read the previously committed (300, 300) mm point. Nonnumeric input `abc` was
also refused without changing the point or consuming undo history. One Undo
restored the original (0, 0) mm corner; InputV1 remained unchanged throughout.
The temporary process was closed after restoring the baseline.

These checks use native 3D picking and Tab/Escape, supported property API entry
and API Undo. They do not prove keyboard focus/typing in the property widget,
all invalid/self-intersecting contours, a full serialized-model diff, or new
behaviour in the pending editor selection slice. The first checker attempt
imported an old command-line helper with side effects; that tooling was guarded
before the passing continuation. No product change was needed.

## Generator boundary

Existing native contour editing does **not** rewrite the generator's InputV1.
The audit confirms that the original snapshot stays unchanged through these
operations. Applying a manual contour change therefore does not mean the
current rectangle-only generator can regenerate it. Input inspection, a separate
proposal and an in-place update are different operations; the latter remains
subject to the agreement in
[issue #22](https://github.com/OpenAEC-Foundation/open-bim-studio/issues/22#issuecomment-6488059232).

**Verdict:** point and edge picking, G preview/cancel, contour commit and one-step
Undo/Redo are usable in the tested flat-ceiling sketch workflow. Corrected
ordinary-selection corner/side handles, general derived-feature selection and
live generator synchronization are still outstanding.
